# verify.md · 按角色验收

目标：证明「该看到的已经能看到」。角色不同，验收路径不同；跨角色对齐见 `roles-qa.md`。

官方页链接见 `index.md` 页面分工 A（DebugView、实时、事件报告）。

## 先定角色

| 角色 | 金标准 | 未通过时 | 协作 |
| --- | --- | --- | --- |
| 开发者 | DebugView 出现目标事件 + 关键参数正确 | `method.md` 开发排障 | 验证后发 **模版 A**（`roles-qa.md`）对齐使用者所见与目标 |
| 使用者 | 实时或「互动度 → 事件」能找到约定事件名 | 先排除选错属性；仍无则转开发者 | 不清楚先模版 D；要对齐开发见闻则答模版 A / 发模版 B |

开发者「有没有效果」= 代码侧 L1 + 使用者模版 A 第 3 题所见不互相矛盾。

## 开发者验收

### 1) 本地 console

非 prod 且 Debug 开时，封装上报应有清晰日志（事件名 + 参数）。  
无日志 → 总开关 / 是否走到调用点。

### 2) DebugView（联调金标准）

```text
https://analytics.google.com/
→ 选对「账号 / 属性」
→ 管理 → 数据展示 → DebugView
→ 保持测试页打开，操作一次
→ 秒级流（中间列）出现 page_view 或目标事件；点开核对参数
→ 多设备时用左上角 DEBUG DEVICE 选自己的设备
```

启用 debug mode：个人设备用 Tag Assistant（tagassistant.google.com）或 GTM 预览模式；全部设备改配置。正式包关闭 debug，并过滤开发者流量。

DebugView 看不到事件的原因：客户端隐私控制；开了 consent mode 但用户未同意 Analytics cookie。

### 3) 实时（可选）

```text
报告 → 实时 → 按事件名称划分的事件数
```

### 通过标准（开发）

| 级别 | 标准 | 可对外说 |
| --- | --- | --- |
| L1 | DebugView 目标事件 + 关键参数正确 | 「埋点已打通」 |
| L2 | 实时也能看到 | 「采集正常（粗）」 |
| L3 | 事件报告稳定出现；需用的自定义维度已登记 | 「可以做分析/漏斗」 |

未达 L1 不得宣称接入完成。

## 使用者验收

不问代码，只带控制台路径；必要时用老板能听懂的句子。

### 运营 / 产品

```text
1. 打开 analytics.google.com → 选对属性
2. 报告 → 实时：是否出现约定事件（官方名或自定义名）
3. 报告 → 互动度 → 事件：目标事件是否在列表（新事件可能晚几小时）
4. 若要漏斗：探索 → 漏斗探索，步骤按 analysis.md 的通用模板裁剪
5. 自定义事件要按参数拆：管理 → 自定义定义 是否已登记
```

通过：能在实时或事件列表指认**事先约定的那个名字**（不要官方名、自定义名混着找）。

### 老板

```text
打开 Analytics → 选对网站属性 →「实时」
看现在有没有活跃用户、关键按钮/下单事件有没有跳。
要看转化：让运营/产品打开「探索 → 漏斗」按约定步骤看断点。
```

通过：实时有活跃；关键转化事件在约定周期内有计数（具体阈值由业务定，AI 不编造）。

### 个人学习

最短实验：

1. 发一个官方事件（如 `login`）+ 一个自定义事件（如 `feature_used`）  
2. DebugView 或实时确认两者都出现  
3. 读 `event-design.md` 对照「为什么一个是官方、一个是自定义」  
4. 按 `analysis.md` 建一个两步漏斗玩一次  

文档入口见各文件链接表。
