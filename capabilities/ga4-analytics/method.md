## 0. 角色场景（每次协助先做）

全文与可复制模版见 **`roles-qa.md`**（重点）。此处只留判定与挂钩。

本地帮助时，**先判断当前发言角色**，再选逻辑。不确定就问：「你现在是在写/改代码（开发者），还是主要看后台 / 要业务结论（使用者）？」

| 角色 | 典型说法 | AI 主线 | 默认读 | 验收 | 模版 |
| --- | --- | --- | --- | --- | --- |
| **开发者** | 接入、埋点、开关、DebugView、有没有效果 | 验证对不对 / 有没有效果 | `setup` / `event-design` / `verify` 开发节 | console → DebugView | 向使用者发 **模版 A** |
| **使用者** | 有没有数、漏斗、转化、事件在哪看 | 不清楚先解答；具体内容再收口 | `analysis` / `verify` 使用者节 | 实时 / 事件 / 探索 | 先 **模版 D**；落地发 **模版 B**；答 **模版 A** |

不变约束：

- 只有开发者与使用者两种角色（可一人兼两角、可多人）。  
- 模版在**阅读本技能之后**发出提问，并在**阅读本技能之后**看到提问再协助回答。  
- 双方互相协助：开发者不只写代码，还要问清使用者所见与目标；使用者不只看数，涉及具体内容要给开发者可执行描述。

使用者话术深浅（仍是同一角色）：

| 侧重 | 话术重点 |
| --- | --- |
| 运营 | 事件是否在列表、活动期对比、漏斗断点 |
| 产品 | 覆盖是否够、该用官方名还是自定义、维度是否够拆 |
| 老板 | 少术语：打开哪页、看哪个数、是否正常 |
| 个人学习 | 官方 vs 自定义 + 最短实验路径 |

禁止：对使用者大段讲注入；对开发者只丢报表路径却不验证效果；跳过模版臆造对方目标。

## 1. 新项目接入（偏开发）

```text
是否已有 GA4 属性与 Web 数据流？
 ├─ 否 → 提示用户打开 analytics.google.com 创建（index「页面分工 B」）
 │         AI 可读官方文档（页面分工 A），不能代登录
 └─ 是 → 拿到 Measurement ID（G-…）
           ↓
         setup.md：开关 / 注入 / PV 策略 / User-ID / 公共参数
           ↓
         event-design.md：先用官方预设，不够再自定义
           ↓
         verify.md · 开发验收
```

使用者若只是「公司还没有 GA」：引导创建属性/数据流 + 把 G-ID 交给开发，**不要**替他改仓库。

## 2. 加 / 改事件

```text
身份？
 ├─ 开发 → 查官方推荐表能否映射
 │         能 → 用 A 类官方名（event-design）
 │         否 → B 类自定义 snake_case + 业务仓字典
 │         → verify 开发节
 └─ 使用者 → 确认事件名是否已上线
           → analysis：事件列表 / 自定义维度 / 是否要标关键事件
           → 需要改埋点则转交开发任务，不要假装已改代码
```

## 3. 排障（没数 / 数不对）

### 开发视角（按序，勿跳步）

| 顺序 | 检查 | 常见结果 |
| --- | --- | --- |
| 1 | 环境总开关 | 测服显式关闭 → 不上报属预期 |
| 2 | 是否 H5/Web 运行时 | 非 Web 条件编译可能未注入 |
| 3 | Network 是否有 `gtag/js` / collect | 无请求 → 注入失败 |
| 4 | `debug_mode` / Debugger 扩展 | DebugView 空但 Realtime 偶有 |
| 5 | 属性是否选对 | 开错账号/属性 |
| 6 | User-ID / 游客 | 登录后维度仍像游客 |
| 7 | 广告拦截 / 隐私模式 | 脚本被拦 |
| 8 | 官方名 vs 自定义名混用 / 双发 | 漏斗双计或「找不到旧名」 |

### 使用者视角

| 顺序 | 检查 | 话术 |
| --- | --- | --- |
| 1 | 属性选对了吗 | 左上角账号/属性是否为目标站 |
| 2 | 实时有没有 | 报告 → 实时；没有则转开发排障 |
| 3 | 事件列表有没有 | 互动度 → 事件；新事件可能延迟 |
| 4 | 看的是官方名还是自定义名 | 两边名字不同会「以为没数」 |
| 5 | 漏斗步骤是否混用双名 | 同义官方+自定义不要同漏斗混放 |

每步结论都要带「下一步打开哪一页」或「去查哪篇文档」。

## 4. 看数 / 漏斗（偏使用者；开发可陪跑）

```text
只要确认「事件打到了」→ verify（开发：DebugView / 使用者：实时）
要看「今天有没有量」→ 报告 → 实时
要看「某事件趋势」→ 互动度 → 事件（自定义同上）
要做「转化路径」→ 探索 → 漏斗；步骤规则见 analysis.md
参数要拆分 → 先自定义定义，再探索
```

## 状态机（给 AI）

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `NEED_ROLE` | 角色未明 | 先问开发者 or 使用者 |
| `NEED_PEER_INFO` | 缺另一方见闻/目标 | 发 `roles-qa` 模版 A 或 B |
| `NO_PROPERTY` | 无属性/数据流 | 提示用户创建 |
| `HAS_ID_NO_CODE` | 有 G-ID，未接入 | 开发者走 `setup.md` |
| `CODE_NO_DEBUG` | 有代码，DebugView 未见 | 开发者排障 + `verify` |
| `DEBUG_OK` | DebugView 可见目标事件 | 联调通过；仍应用模版 A 对齐使用者所见 |
| `REPORT_READY` | 事件报告稳定出现 | 可做探索/漏斗（使用者主责） |
